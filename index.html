角色 · 创建者 / 产品与架构设计 平台 · 企业级 Agent 平台 用户 · 区域运营 / 商业分析 / 管理层
01 · Problem

解决什么问题

PAIN 01

取数低效

经营数据散落在多个看板、数仓与目标系统，一次完整分析需人工切换拼表 2–4 小时。

PAIN 02

归因靠个人经验

同一个"订单为什么降"，不同分析师结论差异大，质量取决于"是谁写的"而非"方法论是否正确"。

PAIN 03

响应滞后

发现问题 → 找分析师 → 人工排查，链路通常 T+1 起，无法支撑及时经营决策。

02 · Architecture

分层能力设计按「解决什么问题」递进建设

L1 · 去哪看

数据查询层

自然语言查数：意图识别（指标 × 时间 × 区域）→ 自动路由到正确数据源（业务看板 / SQL / 指标平台），模糊问法主动追问而非猜测。

L2 · 为什么（核心亮点）

分析诊断层

异动检测 + 多维归因引擎：排除法 + 连环替代法，每个因素量化贡献度（如「天气贡献 -5.2pp」），输出结构化归因报告。

L3 · 怎么办

决策支持层

月度预测、节假日保障、目标拆解（大区→城市）、周/月复盘报告自动生成，形成分析闭环。

架构模式：复用平台原生的 Skill 发现与匹配机制（非自建 Router），自定义业务 Skill 作为方法论增强层，与取数、文档、可视化等通用 Skill 协同编排。

03 · Features

核心功能点

能力设计要点
统一指标查询单指标 / 多指标 / 跨对象对比 / 目标达成查询；每个数值标注来源，可回溯验证
异动归因引擎 ★「先外后内、先大后小」：外部因素（天气/节假日）优先排除 → 供给侧 → 需求侧；拒绝模糊结论，必须量化到 pp 级贡献

分层交互群聊：结论先行、限长、高密级数据不展示明细；私聊：完整报告 + 多轮追问
04 · Quality & Eval

质量与评测体系用户敢用的前提是它不出错

六维评测框架

数据查询准确性 25% · 异动归因质量 25% · 业务知识 15% · 安全合规 15% · 输出规范 10% · 交互体验 10%。每个 case 5 分制，加权 ≥3.5 合格；配套含负样本（如"未达异动阈值不应误判"）的标准测试集。

专家基准评测

以历史周会上专家人工识别并归因过的异动案例作为 ground truth 构建评测集：让 Agent 对同一批历史异动独立跑归因，用「与专家历史结论的一致性」度量准确率——标尺来自业务专家，而非模型自评。

  • 口径一致性铁律：订单 ↔ 收入 ↔ 客单价互为约束，修正任一变量必须重算整个三角并三方校验
  • 幻觉兜底：生成端与验证端不共用同一假设，结论用独立数据源交叉验证；规律用同年实测验证而非模型假设
  • 诚实边界：竞对、政策等无法量化的因素如实说明，不强行凑解释；数据不确定时明说"我不确定"
  • 安全红线：不编造数据、不执行写操作、不访问越权数据、拒绝提示词注入
05 · Agent Engineering

Agent 工程细节

身份与边界

三文件身份体系（身份 / 工作区规范 / 输出人格），能力白名单 + 「不能做的事」明示，不替代人做决策。

记忆分层

长期记忆（容量治理）+ 每日记录 + 跨会话检索三层结构，用户偏好与业务口径主动沉淀。

Skill 工程化

自包含 description、触发词与负样本声明、Fallback 路径、发布校验——保证路由精准与可维护性。
